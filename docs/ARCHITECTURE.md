# Архитектура проекта — 9 октября 2026

## Приложения и хранение

`apps/web` — Next.js/React/TypeScript. `src/app` содержит маршруты; `features` — предметные сценарии, адаптеры API и компоненты; `shared` — язык и подписки. `apps/api` — NestJS/Prisma/PostgreSQL с модулями auth, tournaments, draws, matches, control, tatamis, public и protocols. Next.js проксирует `/api/v1` на локальный API `127.0.0.1:4319`; сайт слушает `127.0.0.1:4318`. Развёртывание для других устройств требует отдельной настройки адресов, HTTPS и разрешённых Origin.

PostgreSQL хранит турниры, категории, заявки, версии сеток, встречи, сессии, приглашения, `MatchEvent` и `AuditEvent`. Подтверждённые результаты долговременные. Отдельного общего справочника спортсменов/клубов нет: заявки разных категорий имеют разные ID. Снимок пользовательского регламента хранится в турнире; параметры категорий фиксируются при запуске.

Состав вводит администратор по одному спортсмену. По уточнению 9 октября файловый импорт исключён; будущий ввод всей команды — вставка обычного текста, предпросмотр с проверкой и отдельное подтверждение. Команда и категории задаются явно, категория не угадывается. Участники уже взвешены вне программы: фактический вес и отметка взвешивания не обязательны. Текстовый ввод команды и полное редактирование состава ещё не реализованы.

DTO проверяют форму команд; сервисы проверяют права, принадлежность турниру, версии, состояние и зависимости. Подготовка состава блокирует строки категории/турнира; критические команды табло и центрального управления выполняются в транзакциях. Подтверждение результата сохраняет состояние, продвигает зависимые позиции, обновляет очереди и записывает историю. Исправление с уже начатыми зависимыми встречами безопасно блокируется. Полный аудит подготовки состава и все процедуры жизненного цикла пока отсутствуют.

Новые команды табло сохраняют исходный ответ вместе с командой. Повтор ID с тем же содержимым возвращает сохранённый ответ; другое содержимое отклоняется. Уникальность вложенных автономных событий проверяется также по историческим пакетам, где отдельные записи событий ещё не создавались. Клиент не применяет старый ответ повторной команды поверх более новой версии встречи.

Подготовительное `/contests/:id/assign` принимает обязательные `id`, `expectedRevision` и `tatamiId`. Назначение повышает revision, сохраняет команду, исходный ответ и аудит в одной транзакции; повтор возвращает исходный ответ без перестановки очереди, смена содержимого ID и устаревшая версия отклоняются. DrawPanel сохраняет команду в sessionStorage до отправки, повторяет неизменный payload после потери ответа/5xx и не заменяет более новое состояние старым receipt. Закрепление категории сохраняется. Изолированная PostgreSQL-репетиция и полный `npm run check` этапа 1 прошли; итоговые наборы содержат 92 теста.

## Доступ

Глобальный `AuthGuard` проверяет серверные сессии. Организаторов создаёт `SUPER_ADMIN`; публичной регистрации нет. Главный администратор имеет доступ ко всем турнирам, организатор — к своим, оператор — к назначенному татами. Приватные LIVE и очереди доступны владельцу, администратору и оператору своего татами; зрителям доступны только опубликованные турниры. Публикация сетки управляется отдельно.

Пароли хешируются scrypt; токены сессий и приглашений хранятся как SHA-256. Cookie использует HttpOnly/SameSite=Strict; HTTPS требует `COOKIE_SECURE=true`. Изменяющие запросы требуют `X-Judo-Client: web` и допустимого Origin. Ограничение попыток хранится в памяти одного процесса и использует общий IP; массовый вход через один прокси требует доработки. По уточнению пользователя от 9 октября нужны две рабочие роли: администратор и судья назначенного табло. Отдельные роли главного судьи и оператора турнира исключены. Обычный результат подтверждает судья табло, административные и исключительные исправления выполняет администратор. Текущие технические роли `SUPER_ADMIN`/`ORGANIZER`/`OPERATOR` и аккаунты сохраняются до этапа 4; этап 1 не меняет модель доступа.

## Спортивное ядро и очередь

`packages/engine` — независимый TypeScript-пакет с публичными экспортами `@judo/engine/match` и `@judo/engine/draw`. Нет React, HTTP, БД и DOM. Его используют сервер и подготовленный автономный пульт. `features/scoreboard/model/use-match` обслуживает отдельно обозначенную демонстрацию. Демонстрационные данные хранятся в fixtures.

Новый профиль `custom-2026-v3` использует круговую систему для 2–7 спортсменов; с 8 доступны круговая, олимпийская с утешением и смешанная с утешением. Исторические сетки сохраняют прежний профиль. Соответствие официальному IJF не подтверждено.

Категория закреплена за одним татами. Автораспределение сохраняет закрепления и учитывает все оставшиеся встречи. Порядок: круг → младшая возрастная группа → лёгкий вес → стабильный порядок. Сервер проверяет барьер кругов, занятость и отдых перед стартом. Перенос одной встречи не меняет основное татами категории. Отдых сейчас отсчитывается от `confirmedAt`; это может излишне задерживать старт при позднем подтверждении результата. Отдельное время фактического окончания и общий ID спортсмена между категориями ещё нужны.

## Автономность и обновления

Автономный режим заранее открывается на сервере для текущей остановленной встречи. Web Locks ограничивает управление вкладкой; Service Worker сохраняет оболочку, IndexedDB — события и новое состояние одной локальной транзакцией. Восстановление журнала предшествует новым онлайн-командам. После перезагрузки работающий таймер переводится на паузу. При передаче управления серверу новые локальные события блокируются, чтобы не потерять их после ответа.

Пакеты проверяются и применяются сервером атомарно, включая права, владельца, версии, непрерывность и ID каждого события. Несинхронизированный результат не продвигает сетку. Ошибка записи блокирует локальное управление; конфликт сохраняет журнал для ручной сверки. Редактор сравнения конфликтующих ветвей и физические испытания в зале ещё нужны.

Сейчас используется `ws`, без Socket.IO и Redis. WebSocket передаёт уведомления, клиенты перечитывают снимки HTTP и периодически повторяют запросы. В обзорах чтения сериализованы, всплески уведомлений объединяются; закрытый экран не принимает запоздалый ответ. При временном сбое табло показывает последнее состояние с отметкой потери связи; при отзыве доступа очищает его. Heartbeat удаляет соединения без pong.

Транзакционного outbox, воспроизведения событий по курсору и нескольких экземпляров API пока нет. Периодические HTTP-запросы восстанавливают актуальное состояние после пропущенного уведомления, но не заменяют требуемую ТЗ гарантированную доставку. Переход к Socket.IO/Redis/outbox и Docker остаётся явным архитектурным долгом.

## PDF и проверки

PDF генерируется сервером из согласованного снимка PostgreSQL с `RepeatableRead`, на русском и казахском со встроенными шрифтами. Доступны сетки и участники; остальные виды отложены по последнему решению пользователя. Сохранённый PDF — снимок на момент скачивания; автоматического хранения версий документов пока нет.

`npm run check` проверяет формат, границы всех приложений, строгие типы, регрессии ядра/интерфейса/API/скриптов и production-сборку. `test:api` работает без БД. `test:rehearsal` создаёт отдельную схему PostgreSQL, запускает отдельный API, проверяет интеграцию и восстановление после реальных перезапусков, затем удаляет только свою схему. `npm run dev` управляет группами дочерних процессов на macOS/Linux, включая корректную остановку потомков npm. Репетиция на устройствах зала и нагрузочная приёмка остаются обязательными.

`npm run db:backup:verify` выгружает согласованный read-only снимок текущей схемы приложения с UUID через `pg_dump`, восстанавливает его только в созданную скриптом QA-базу и сравнивает данные таблиц, колонки с точностью времени, ограничения и индексы. Проверяются и записи миграций; SQL NULL отличим от JSON null. Неподдерживаемые объекты будущей схемы приводят к отказу проверки, а не к общему утверждению о восстановлении произвольной БД. QA-база удаляется; приватный архив и манифесты остаются в `tmp/backups`, публичный отчёт — `docs/reports/latest-backup-verification.json`. Проверка текущего снимка прошла; она не охватывает IndexedDB, файлы assets, права пользователей PostgreSQL и восстановление оборудования. Требования запуска описаны в README.

Локальный Git инициализирован; проверенная версия исходников сохраняется в локальной истории Git. `.env` и приватные дампы исключены из истории. Резервные копии исходников сохранены в `tmp/audit-backups` и `tmp/stage1-backups`.

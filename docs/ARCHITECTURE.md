# Архитектура проекта — 10 октября 2026

## Приложения и хранение

`apps/web` — Next.js/React/TypeScript. `src/app` содержит маршруты; `features` — предметные сценарии, адаптеры API и компоненты; `shared` — язык и подписки. `features/roster` отделяет редактор состава, разбор текста, модель проверки и адаптер команд. `apps/api` — NestJS/Prisma/PostgreSQL с модулями auth, tournaments, roster, draws, matches, control, tatamis, public и protocols. Next.js проксирует `/api/v1` на локальный API `127.0.0.1:4319`; сайт слушает `127.0.0.1:4318`. Развёртывание для других устройств требует отдельной настройки адресов, HTTPS и разрешённых Origin.

PostgreSQL хранит турниры, категории, клубы текущего турнира, заявки, версии сеток, встречи, сессии, приглашения, `MatchEvent`, `RosterCommand` и `AuditEvent`. Подтверждённые результаты долговременные. `Club` имеет ID и нормализованное уникальное название внутри турнира; `Entry.clubId` связывает заявку с клубом, `Entry.gender` явно хранится для новых строк. `Athlete` хранит стабильный ID и владельца истории; обязательный `Entry.athleteId` связывает самостоятельные снимки заявок разных турниров. Канонической общей карточки ФИО и глобального клуба нет. Одна активная заявка спортсмена в турнире означает одну категорию; новые однофамильцы не объединяются автоматически. Снимок пользовательского регламента хранится в турнире; параметры категорий фиксируются при запуске.

Администратор один раз выбирает или создаёт клуб, затем вводит команду строками с фамилией, именем, годом рождения, полом и явной категорией. Необязательная вставка текста `Фамилия;Имя;Год рождения;Пол;Точное название категории` (или табуляция, необязательный заголовок) наполняет тот же редактируемый черновик. Категория не угадывается; неизвестное или неоднозначное название требует ручного выбора. Предпросмотр не меняет БД и счётчики. RU/KK, просмотр по клубам/категориям, дополнение состава, исправление одной заявки, архив/восстановление и явный выбор спортсмена из истории реализованы. Исправление общей связи отделено от редактирования личных данных заявки. Excel/файлы исключены. Участники уже взвешены вне программы: фактический вес и отметка взвешивания не обязательны.

`POST /tournaments/:id/clubs` и `POST /tournaments/:id/roster` требуют ID команды и `expectedRevision`; турнир имеет `rosterRevision`. `POST /tournaments/:id/roster/preview` проверяет полный согласованный снимок без записи. Пакет до 500 строк записывается целиком либо отклоняется; в категории максимум 128 участников. Возможные совпадения требуют явного подтверждения отдельного спортсмена, без объединения по имени; ответ содержит общее число совпадений и первые пять примеров. После запуска турнира или подтверждения сетки категории новые строки блокируются. Команда, исходный ответ и аудит сохраняются одной транзакцией. Точный повтор возвращает receipt; устаревшая версия и изменённый payload того же ID отклоняются.

Браузер сохраняет черновики и неизменяемую pending-команду в `sessionStorage` по турниру/клубу до отправки. Это восстановление после reload в той же вкладке, без гарантии после её закрытия и без замены долговременного хранения. Неизвестный результат после сети/5xx блокирует новую команду и повторяется с прежним ID/revision/body; явный отказ обновляет данные и требует новой проверки. Workspace сериализует HTTP-чтения; более старая `rosterRevision` и старые receipts не заменяют новое состояние. Старый endpoint индивидуального добавления сохраняется для совместимости, но не имеет всех гарантий нового API состава.

Миграция клубов требует PostgreSQL 18+ и UTF8: для согласованной нормализации Unicode используется `pg_catalog.pg_unicode_fast`; описание сортировки — [PostgreSQL 18](https://www.postgresql.org/docs/18/collation.html). Она применена к рабочей БД: значения всех старых колонок 12 таблиц сохранились, 34 существующие заявки связаны с четырьмя клубами без изменения имён и исторического пола. Отчёт — `docs/reports/latest-working-roster-migration.json`. Интеграционная репетиция и Safari QA выполнялись отдельно на удаляемых QA-данных; применение миграции не считается эксплуатационной приёмкой.

Каталог спортсменов ограничен владельцем целевого турнира; SUPER_ADMIN использует тот же scope. У турнира без владельца каталог ограничен его собственными заявками. Параметризованный SQL фильтрует NFKC/Unicode слова по авторизованным историческим снимкам перед LIMIT; Prisma загружает только последний snapshot и активную заявку текущего турнира. Привязка неподтверждённой заявки требует отдельного preview/reason/revision/receipt/audit и сохраняет её личные поля. Подтверждённая сетка или любая ссылка Contest делает связь неизменяемой. Массовое объединение, новая идентичность для сохранённой заявки и возврат к идентичности без оставшихся снимков каталога не реализованы.

Отдельный `POST /tournaments/:id/roster/entries/:entryId/name` исправляет только `firstName`/`lastName` активной Entry текущего турнира. Допустимы DRAFT с CONFIRMED целевой сеткой, RUNNING и FINISHED. После Tournament/Tatami/Session/command-ID/Category/Entry locks сервер повторно проверяет живого администратора, scope и версию состава; нормализованные имена, `RosterCommand` receipt и аудит сохраняются одной транзакцией. ID, `athleteId`, raw nullable-поля, клуб/категория, спортивные состояния, версии сетки и управление не меняются. Старый receipt не откатывает новую `rosterRevision`; повтор доступен тому же живому автору. `features/roster` использует один serial pending-барьер для всех операций, сохраняет исходный пакет до POST и после reload, проверяет неизменность остальных полей receipt; неизвестный исход требует exact retry/выгрузки.

DTO проверяют форму команд; сервисы проверяют права, принадлежность турниру, версии, состояние и зависимости. Новый ввод состава, критические команды табло и центрального управления выполняются в транзакциях. Подтверждение результата сохраняет состояние, продвигает зависимые позиции, обновляет очереди и записывает историю. Исправление с уже начатыми зависимыми встречами безопасно блокируется. Аудит нового клубного ввода реализован; полнота исторического API состава и все процедуры жизненного цикла пока не обеспечены.

Новые команды табло сохраняют исходный ответ вместе с командой. Повтор ID с тем же содержимым возвращает сохранённый ответ; другое содержимое отклоняется. Уникальность вложенных автономных событий проверяется также по историческим пакетам, где отдельные записи событий ещё не создавались. Клиент не применяет старый ответ повторной команды поверх более новой версии встречи.

Подготовительное `/contests/:id/assign` принимает обязательные `id`, `expectedRevision` и `tatamiId`. Назначение повышает revision, сохраняет команду, исходный ответ и аудит в одной транзакции; повтор возвращает исходный ответ без перестановки очереди, смена содержимого ID и устаревшая версия отклоняются. Живая Session повторно проверяется внутри транзакции после Tournament/Tatami locks и до нового изменения или получения receipt, с согласованным порядком logout/CLAIM. DrawPanel сохраняет команду в sessionStorage до отправки, повторяет неизменный payload после потери ответа/5xx и не заменяет более новое состояние старым receipt. Закрепление категории сохраняется. Изолированная PostgreSQL-репетиция и полный `npm run check` этапа 1 прошли; итоговые наборы содержат 92 теста.

## Доступ

Глобальный `AuthGuard` проверяет серверные сессии. Организаторов создаёт `SUPER_ADMIN`; публичной регистрации нет. Главный администратор имеет доступ ко всем турнирам, организатор — к своим, оператор — к назначенному татами. Приватные LIVE и очереди доступны владельцу, администратору и оператору своего татами; зрителям доступны только опубликованные турниры. Публикация сетки управляется отдельно.

Пароли хешируются scrypt; токены сессий и приглашений хранятся как SHA-256. Cookie использует HttpOnly/SameSite=Strict; HTTPS требует `COOKIE_SECURE=true`. Изменяющие запросы требуют `X-Judo-Client: web` и допустимого Origin. Ограничение попыток хранится в памяти одного процесса и использует общий IP; массовый вход через один прокси требует доработки. По уточнению пользователя от 9 октября нужны две рабочие роли: администратор и судья назначенного табло. Отдельные роли главного судьи и оператора турнира исключены. Обычный результат подтверждает судья табло, административные и исключительные исправления выполняет администратор. Технические роли `SUPER_ADMIN`/`ORGANIZER`/`OPERATOR` и существующие аккаунты сохранены. `workRole` отображает `ADMIN`/`JUDGE`; системный доступ, область владельца турнира и назначение судьи проверяются сервером.

На каждом татами один серверный владелец пульта: живая Session, UUID вкладки и `controlGeneration`. `CLAIM`, `RELEASE` и административный `TAKEOVER` используют отдельную `accessRevision`, неизменяемый ID команды, сохранённый ответ и аудит. Дублированная вкладка получает другой UUID через Web Locks. Закрытие или истечение сессии не открывает управление следующему устройству автоматически: прежнее назначение сохраняется до явной передачи.

Новые команды встречи проверяют Session и допуск внутри транзакции. Старый точный receipt доступен тому же живому автору до проверки текущего допуска и не меняет состояние. Порядок блокировок: Tournament → Tatami в стабильном порядке → Session → Contest → ID команд → Athlete. Административные изменения повышают поколение допуска затронутого татами. При истёкшем/отозванном доступе или передаче работающий таймер ставится на паузу по последнему сохранённому времени; удержание, оценки и резерв спортсмена остаются. В событии и аудите указывается `clockUncertain`; после явной сверки администратору доступна корректировка остановленного времени этапа 5а.

`AccessCommand` сохраняет нормализованную команду и исходный ответ. Приглашение хранит SHA-256 токена; plaintext не входит в receipt или аудит. Принятие одноразовое, Session ограничена сроком приглашения и максимумом 8 часов. Выдача и отзыв имеют ID/revision и точный повтор. Историческая автономная сессия с `offlineControlGeneration=null` блокируется до административного разбора. Старый или чужой журнал не перепаковывается под новый допуск; история и выгрузка сохраняются. Проверки внедрения описаны в STATUS.md.

## Спортивное ядро и очередь

`packages/engine` — независимый TypeScript-пакет с публичными экспортами `@judo/engine/match` и `@judo/engine/draw`. Нет React, HTTP, БД и DOM. Его используют сервер и подготовленный автономный пульт. `features/scoreboard/model/use-match` обслуживает отдельно обозначенную демонстрацию. Демонстрационные данные хранятся в fixtures.

Профиль `custom-2026-v3` использует круговую систему для 2–7 спортсменов; с 8 доступны круговая, олимпийская с утешением и смешанная с утешением. Поведение оценок, удержания и Golden Score едино, различается длительность основного времени категории. Исторические сетки сохраняют прежний профиль. Соответствие официальному IJF не подтверждено.

Ранжирование v3 ещё использует head-to-head и автоматические дополнительные серии, что не соответствует последнему правилу: только число побед; двое равных — новая встреча независимо от личной; трое и более — ручная сверка администратора. Планируемый v4 должен иметь общий публичный расчёт `drawProgress` с ожидаемой ручной сверкой, требуемыми парами, барьером стадии и окончательными местами, одинаковый для API/UI/PDF. Отсутствие новой Contest при ручной сверке не означает завершения категории. MIXED удерживает весь плей-офф в WAITING до разрешения всех групп; сдвиг следующих стадий затрагивает только ещё не начатые встречи со стабильными ID. FINISHED и TEAMS требуют разрешённых мест, а не только счётчика подтверждений. Политика выбора дополнительной серии или ручных пар ещё должна быть согласована; произвольное назначение победителя не является готовой процедурой.

Публичный чистый `correctStoppedClock` исправляет время без добавления команды в судейский или автономный журнал. Серверный `EDIT_TIME` доступен только администратору для `Contest.ACTIVE` с состоянием `PAUSED`/`DECISION`, без HOLD, offline lease и исхода. Отдельно допускается неподтверждённый `PROVISIONAL` основного времени с основанием `TIME`: при восстановлении времени этот исход снимается, оценки и их история сохраняются. Основное elapsed ограничено длительностью встречи, Golden Score — техническим пределом 6 часов. Фаза не меняется, часы остаются остановленными. На точной границе основного времени действует существующий расчёт исхода; `DECISION` при уменьшении времени возвращается в `PAUSED`. Подтверждённые результаты и остальные предварительные исходы не исправляются этим методом.

`GET /tournaments/:id/control/:contestId/impact` отдаёт `revision`, `impactToken`, зависимости, `stoppedClock` и `clockState` без внутренних receipts. Подпись включает поля текущей и зависимых встреч, полный спортивный снимок с очищенными receipts и поля offline lease/generation. Обычный тик может изменить время или промежуточную оценку удержания без повышения `Contest.revision`; такое изменение всё равно делает прежний preview недействительным (`IMPACT_CHANGED`). Терминальный онлайн-переход RUNNING→DECISION/PROVISIONAL повышает revision один раз и атомарно сохраняет `CLOCK_TERMINAL_REACHED` и `MATCH_CLOCK_TERMINAL_REACHED` с исходным/новым состоянием и причиной окончания времени либо результата удержания. Повторный tick не дублирует событие или оценку, ошибка аудита откатывает весь переход. Это не заменяет отдельное подтверждение результата и будущий endedAt для отдыха. Команда `EDIT_TIME` требует прежний token/revision, фазу, целое `elapsedMs` и причину. Под живой Session и shared Athlete locks сервер сохраняет новое состояние, повышает версии встречи и допуска, убирает временную опору и записывает аудит. `MatchEvent.payload` хранит неизменяемые `{command, response}`; точный повтор того же живого автора возвращает исходный ответ до проверки нового impact, не откатывая состояние.

`features/control` отделяет форму и предпросмотр времени, адаптер административных команд и модель pending-пакета. Для REGULAR интерфейс вводит оставшееся, для GOLDEN — прошедшее время с десятыми; preview использует тот же публичный helper. Pending-команда сохраняется до POST в `sessionStorage` текущей вкладки и после reload повторяется с исходными ID/revision/token/body. Неизвестный ответ, в том числе потеря доступа, блокирует новую команду; пакет можно выгрузить или архивировать после явной сверки. Локальный архив сохраняет исходный пакет и причину, но не отменяет серверное действие и не гарантирует хранение после закрытия вкладки.

Категория закреплена за одним татами. Автораспределение сохраняет закрепления и учитывает все оставшиеся встречи. Порядок: круг → младшая возрастная группа → лёгкий вес → стабильный порядок. Сервер проверяет барьер кругов, занятость и отдых перед стартом. Перенос одной встречи не меняет основное татами категории. Отдых сейчас отсчитывается от `confirmedAt`; это может излишне задерживать старт при позднем подтверждении результата. Общий ID используется для busy/rest между турнирами. Shared Athlete locks берутся в отсортированном порядке после локальных Tournament/Tatami/Contest/command-ID locks; получение и освобождение резерва сериализованы, чужие спортивные строки после этого читаются без блокировки. Пауза/PROVISIONAL/offline сохраняют ACTIVE. REOPEN исключает собственный результат из отдыха, но учитывает другие завершённые встречи. Отдельное время фактического окончания ещё нужно.

Запуск и распределение используют один scope непустых категорий: пустые настройки и их старые STALE-сетки остаются сохранёнными, но не мешают участвующим категориям. Отсутствие непустых категорий возвращает `NO_ACTIVE_CATEGORIES`; один участник — `CATEGORY_NEEDS_OPPONENT`, без автоматического золота или фиктивной пары. Для остальных требуется подтверждённая сетка. Сортировка открытых весовых категорий при равном возрасте учитывает нижнюю границу, после категорий с заданным верхним пределом.

Три Shido завершают только текущую встречу; проигравший остаётся доступным для предусмотренного сеткой пути к бронзе. Административное снятие в любой момент турнира планируется после v4/барьеров стадий, с сохранением Entry/Contest и истории. Политика текущего предварительного исхода, будущих WALKOVER, снятий в группе, пустых ветвей и уже заработанных мест ещё согласуется. Автоматический каскад проведённых зависимых встреч и переоткрытие группы с созданными дополнительными кругами не реализованы; последнее блокируется `TIEBREAK_REVIEW_REQUIRED`.

## Автономность и обновления

Автономный режим заранее открывается на сервере для текущей остановленной встречи. Web Locks ограничивает управление вкладкой; Service Worker сохраняет оболочку, IndexedDB — события и новое состояние одной локальной транзакцией. Восстановление журнала предшествует новым онлайн-командам. После перезагрузки работающий таймер переводится на паузу. При передаче управления серверу новые локальные события блокируются, чтобы не потерять их после ответа.

Пакеты проверяются и применяются сервером атомарно, включая права, владельца, версии, непрерывность и ID каждого события. Несинхронизированный результат не продвигает сетку. Ошибка записи блокирует локальное управление; конфликт сохраняет журнал для ручной сверки. Редактор сравнения конфликтующих ветвей и физические испытания в зале ещё нужны.

Единый `hasOfflineOwnership` считает любое non-null поле lease автономным владением; `hasIncompleteOfflineOwnership` отклоняет неполный/некорректный набор. Новые команды, CLAIM/RELEASE/TAKEOVER, tick, административные изменения и TEAMS используют согласованные проверки; старый точный receipt не применяет действие повторно. Полный валидный lease освобождается администратором после сверки. Неполные исторические метаданные блокируются с сохранением исходного журнала; полноценный интерфейс безопасного ремонта всех таких случаев пока не реализован.

Сейчас используется `ws`, без Socket.IO и Redis. WebSocket передаёт уведомления, клиенты перечитывают снимки HTTP и периодически повторяют запросы. В обзорах чтения сериализованы, всплески уведомлений объединяются; закрытый экран не принимает запоздалый ответ. При временном сбое табло показывает последнее состояние с отметкой потери связи; при отзыве доступа очищает его. Heartbeat удаляет соединения без pong.

Notice `roster` обновляет отображаемые имена по Entry ID в подключённых пультах, очереди, сетках и публичных страницах. Для автономной встречи `refreshParticipantNames` накладывает только firstName/lastName при совпадении турнира, текущей Contest и обеих Entry ID; сохранённые state/events/pending остаются неизменными. Без связи новые имена неизвестны до получения актуального HTTP-снимка. Серверный PDF joins текущие Entry внутри своего согласованного чтения, ранее скачанный документ остаётся снимком.

Транзакционного outbox, воспроизведения событий по курсору и нескольких экземпляров API пока нет. Периодические HTTP-запросы восстанавливают актуальное состояние после пропущенного уведомления, но не заменяют требуемую ТЗ гарантированную доставку. Переход к Socket.IO/Redis/outbox и Docker остаётся явным архитектурным долгом.

## PDF и проверки

PDF генерируется сервером из согласованного снимка PostgreSQL с `RepeatableRead`, на русском и казахском со встроенными шрифтами. Доступны сетки и результаты (включая итоговые места после подтверждения категории), участники по категориям и командный зачёт по медалям. До соревнования тот же вид сетки показывает пары без определённых призёров. Отдельные протоколы схваток/итогов, отдельный медальный зачёт и общий комплект исключены из пользовательского сценария. Исторические внутренние типы и render-код сохраняются; сервер продолжает блокировать недоступные виды. Сохранённый PDF — снимок на момент скачивания; автоматического хранения версий документов и публичного скачивания пока нет.

Все запрошенные ID категорий проверяются до отбора scope. Для DRAW и TEAMS пустые категории исключаются; PARTICIPANTS сохраняет выбранные пустые настройки. `protocol-readiness` разрешает TEAMS только для полностью завершённых выбранных категорий: подтверждённая сетка, точные наборы match/contest keys и состава, подтверждённые победители и пары, корректные зависимости и итоговые места, отсутствие offline lease и его оставшихся полей. Иначе `TEAMS_NOT_READY` перечисляет категории и причины; неполный выбранный набор не превращается в частичный итог. Заголовок отличает все категории от выбранной части; включённые категории перечисляются. Клубы ранжируются по золоту, серебру и бронзе, равенство даёт общее место; баллы не применяются. Вёрстка PDF задаёт поля явно, измеряет ячейки и строки, ограничивает текст границами ячеек и резервирует место для заголовков при переходе страницы; визуальная проверка печати остаётся частью приёмки.

`npm run check` проверяет формат, границы всех приложений, строгие типы, регрессии ядра/интерфейса/API/скриптов и production-сборку. Для нового клубного состава полный check прошёл: 124 теста. Изолированный PostgreSQL-прогон прошёл 11 интеграционных наборов, включая roster/protocols, два SIGKILL и один штатный перезапуск с сохранением клубов/состава и повтором исходных receipts. Safari QA проверил ручной ввод/текст, неизменность счётчиков preview, сохранение/reload, список по категориям и RU/KK; viewport 390×844 подтвердил адаптацию полей и доступный фокус. Это не испытание на физических телефонах/ТВ. `test:api` работает без БД. `test:rehearsal` создаёт отдельную схему PostgreSQL, запускает отдельный API, проверяет интеграцию и восстановление после реальных перезапусков, затем удаляет только свою схему. `npm run dev` управляет группами дочерних процессов на macOS/Linux, включая корректную остановку потомков npm. Репетиция на устройствах зала и нагрузочная приёмка остаются обязательными.

`npm run db:backup:verify` выгружает согласованный read-only снимок текущей схемы приложения с UUID через `pg_dump`, восстанавливает его только в созданную скриптом QA-базу и сравнивает данные таблиц, колонки с точностью времени, ограничения и индексы. Проверяются и записи миграций; SQL NULL отличим от JSON null. Неподдерживаемые объекты будущей схемы приводят к отказу проверки, а не к общему утверждению о восстановлении произвольной БД. QA-база удаляется; приватный архив и манифесты остаются в `tmp/backups`, публичный отчёт — `docs/reports/latest-backup-verification.json`. Проверка после миграции доступа этапа 4 прошла: 16 таблиц и структура совпали, QA-база удалена; приватный архив — `tmp/backups/verified-2026-10-09T16-40-53.784Z-73552c7d/database.dump`. Миграция сохранила прежние значения 15 таблиц, отчёт — `docs/reports/latest-working-access-migration.json`. Это доказательства этапа 4; результаты текущего этапа фиксируются в STATUS.md. Проверка не охватывает IndexedDB, файлы assets, права пользователей PostgreSQL и восстановление оборудования. Требования запуска описаны в README.

Локальный Git инициализирован; проверенная версия исходников сохраняется в локальной истории Git. `.env` и приватные дампы исключены из истории. Резервные копии исходников сохранены в `tmp/audit-backups`, `tmp/stage1-backups` и `tmp/club-roster-backups`.
